以下依 Vertica 官方 release notes 逐條整理，模組名稱保留英文原文，說明以中文改寫、內容對應原文，不另加評論。

## 24.2.0-13（Updated 11/16/2026）

| Issue Key | Application Module | 說明 |
|---|---|---|
| `118727` | UI - Management Console | 修補 Kafka 套件內過時 Log4j 函式庫版本（2.25.1、2.25.4）中被識別出的安全漏洞；該函式庫已升級至 2.25.5 版以完成修補 |
| `118697` | Backup/DR | vbr.py 改用時區感知的 UTC 呼叫，取代已棄用的 naive UTC 呼叫 |
| `118231` | Data Loader | 修復可能造成叢集失敗的問題 |
| `25430` | Backup/DR | VBR init 任務現在會正確套用伺服器端加密（SSE）設定 |
| `24685` | Optimizer | 單一查詢中特定組合的運算式、子連結與 group by 可能導致內部錯誤；此問題已解決 |
| `24209` | Backup/DR | 自 23.4 及更早版本升級後排入的 tombstone 物件其位置可能為空；現改用預設儲存位置，以避免可能的 SIGSEGV |
| `24134` | Backup/DR | 處理 load_snapshot 操作期間觀察到的效能瓶頸 |
| `22084` | Optimizer | 某些情況下，具型別轉換的 union 子查詢可能導致型別衝突與內部錯誤；此問題已解決 |
| `21673` | Optimizer | 某些情況下，分析統計值處理 projection 時可能遇到內部型別不符，造成 Optimizer assert 失敗；其成因已解決 |
| `20719` | AMI | EE Data Target Proxy 因網路錯誤失敗的查詢現在可重試，Vertica server 可以其重試機制緩解此類失敗 |
| `20292` | EON | 先前以錯誤的計數器決定交易日誌大小，導致截斷損毀的交易檔時截掉過多內容；現改用正確的計數器存放大小，只正確截斷最後一個交易檔 |
| `20118` | Catalog Engine | OCC 鎖定模式下的並行序號產生現在可容忍 LockTimeout 設為零；不再立即失敗，而是等待至多 LockTimeout 加上新 knob MinOCCLockTimeout 的時間 |
| `16083` | Data Networking | 修復升級至 Vertica 25.3.0-2 後不久資料庫停滯的高嚴重性問題（MinTLSVersion 設為 3 時尤為明顯）；該修復包含於 VER 25.3.0-5，確保資料庫穩定、SQL 查詢不再卡在所有節點 |
| `16037` | Data Networking | TS callback 解構子現在於鎖之外執行，避免死結並提升整體系統穩定性 |
| `13262` | Catalog Engine | 修復執行 ALTER TABLE 命令時發生的節點當機；當機由 VAssert 錯誤觸發（官方頁面此列顯示截斷，後續內容官方未列出） |
| `13141` | Execution Engine | 計畫中使用內部暫存關聯的特定複雜查詢可能報錯或輸出重複列；此問題已修復 |
| `12684` | Execution Engine | 修復與記憶體配置相關的 VAssert 失敗觸發的節點當機（官方頁面此列顯示截斷，後續內容官方未列出） |
| `2711` | Execution Engine | 修復重複使用的 Common Table Expression（CTE）在多個不同聚合子句中被參照時的問題；現於頂層裁剪 CTE，確保整個查詢的欄位參照正確 |
| `2590` | Optimizer | 修復含 Common Table Expression（CTE）與 UNION 操作的複雜查詢間歇性觸發 Internal Optimizer Error (11) 的問題；無需再以 EnableWITHTempRelReuseLimit 等變通方式處理 |
| `2578` | Execution Engine | 24.1 版加入保留 hash/merge right outer join 外側排序性的增強，在 merge join 下可能造成排序違規（此例中與聚合函式產生不一致結果）；現遇到 merge join 時加回明確的 Sort 路徑以維持排序 |
| `2550` | System: Performance | 修正掃描欄位的追蹤方式：11.1 版 resharding 功能為所有掃描加上分割欄位追蹤，即使不需要；現僅在查詢或 reshard 情境確實需要時才追蹤分割欄位 |
| `1198` | Security | 修補 Vertica 隨附第三方元件中被識別出的多個高與重大嚴重性 CVE，涵蓋 Go（vertica-client-proxy）、grpc-go（Node Management Agent）、Log4j（Kafka 套件）及多個 Python 相依套件（cryptography、pyOpenSSL、PyNaCl、pip、Werkzeug、pyasn1、wheel、jaraco.context） |
| `1093` | MC | 修補特定 cookie 未設定 HTTP Only 旗標的安全漏洞（CVE-2025-12454）；缺少該旗標會讓客戶端腳本存取 cookie，增加竊取與注入風險 |
| `1081` | Security | 修補重大安全漏洞 CVE-2026-34480，影響 Vertica Database Cluster 內 Kafka 套件使用的 Log4j 函式庫；已自 2.17.1 升級至建議的修復版本 2.25.4 |
| `1066` | MC | 修補被識別出的重大安全漏洞（CVE-2025-12453），性質為反射型跨站腳本（Reflected Cross-Site Scripting），主要影響 10.0.1 版。在此修正之前，已通過驗證的攻擊者可利用特定 Web UI 端點中未受管控的輸入參數，注入並執行任意 JavaScript 程式碼。本次更新包含相關安全強化，並確保使用者輸入經過適當的清理與中和處理 |
| `987` | Kafka Integration | 修補重大安全漏洞 CVE-2025-68161，位於 org.apache.logging.log4j_log4j-core 2.17.1 版（於 container_minimal_arm 環境的 Prisma 掃描中發現）；Log4j core 函式庫已升級至 2.25.3 版 |
| `957` | Admin Tools | 此前 AdminTools restart_node 可能找到次要 UP 節點執行 catalog editor 取得 catalog 資訊；現一致找到主要 UP 節點，確保取得正確且最新的 catalog 資訊 |
