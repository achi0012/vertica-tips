Each entry below corresponds to the Issue Key, Application Module, and Description in the official Vertica release notes. Module names are kept in their original English form; the descriptions are translated and edited from the original without commentary.

## 24.2.0-13 (Updated 11/16/2026)

| Issue Key | Application Module | Description |
|---|---|---|
| `118727` | UI - Management Console | This update addresses security vulnerabilities identified in outdated Log4j library versions (2.25.1 and 2.25.4) used within the Kafka package; the library has been upgraded to version 2.25.5 to remediate the vulnerabilities |
| `118697` | Backup/DR | The vbr.py script now uses timezone-aware UTC calls instead of deprecated naive UTC calls |
| `118231` | Data Loader | Fixed an issue that could cause a cluster failure |
| `25430` | Backup/DR | Server-side encryption (SSE) settings are now correctly applied during the VBR init task |
| `24685` | Optimizer | Certain combinations of expressions, sublinks, and group by used in a single query could result in an internal error; this has been resolved |
| `24209` | Backup/DR | Tombstone objects can have empty locations if queued after an upgrade from version 23.4 and older; the default storage location is now used to avoid possible SIGSEGV |
| `24134` | Backup/DR | This update addresses a performance bottleneck observed during the load_snapshot operation |
| `22084` | Optimizer | In some cases, union sub-queries with coercion could result in type conflicts and an internal error; this issue has been resolved |
| `21673` | Optimizer | In some cases, analyzing statistics could encounter internal type mismatches when processing projections, causing an Optimizer assert failure; the cause of these mismatches has been resolved |
| `20719` | AMI | Queries failing due to network errors in the EE Data Target Proxy are now retryable, allowing the Vertica server to mitigate such failures with its retry mechanism |
| `20292` | EON | The transaction log size used to be determined from a wrong counter, truncating a corrupted transaction file more than necessary; the size is now stored with the correct counter so only the last transaction file is truncated correctly |
| `20118` | Catalog Engine | Concurrent sequence generation in OCC lock mode can now tolerate a LockTimeout setting of zero; instead of failing immediately, it waits up to LockTimeout plus a new knob called MinOCCLockTimeout |
| `16083` | Data Networking | Fixed a high-severity issue where the Vertica database would hang shortly after upgrading to version 25.3.0-2, particularly when MinTLSVersion was set to 3; the fix, included in VER 25.3.0-5, ensures database stability and prevents SQL queries from getting stuck on all nodes |
| `16037` | Data Networking | TS callback destructors now execute outside of the lock, preventing deadlocks and improving overall system stability |
| `13262` | Catalog Engine | Fixed a node crash issue that occurred when running ALTER TABLE commands, triggered by a VAssert error (this row is truncated on the official page; the remainder is not listed) |
| `13141` | Execution Engine | Certain complex queries using internal temp relations in their plans could either error or output duplicate rows; this issue has been fixed |
| `12684` | Execution Engine | Fixed a node crash triggered by a VAssert failure related to memory allocation (this row is truncated on the official page; the remainder is not listed) |
| `2711` | Execution Engine | Fixed an issue with reused Common Table Expressions (CTEs) when they are referenced in multiple distinct aggregate clauses; the CTE is now pruned at the top level so the whole query has correct column references |
| `2590` | Optimizer | Fixed an issue where complex queries involving Common Table Expressions (CTEs) and UNION operations could intermittently trigger an Internal Optimizer Error (11); no workarounds such as adjusting EnableWITHTempRelReuseLimit are needed anymore |
| `2578` | Execution Engine | An enhancement added in 24.1 preserved the outer's sortedness for hash/merge right outer joins where compatible, which could cause a sort violation under merge join (producing inconsistent results with aggregate functions in this case); an explicit Sort path is now added back for merge joins to preserve ordering |
| `2550` | System: Performance | Changed how scan columns are tracked: the 11.1 resharding feature added segmentation-column tracking to all scans even when unneeded; segmentation columns are now tracked only when specifically needed for the query or a reshard scenario |
| `1198` | Security | This update addresses multiple high- and critical-severity CVEs in third-party components bundled with Vertica, including Go (vertica-client-proxy), grpc-go (Node Management Agent), Log4j (Kafka package), and several Python dependencies (cryptography, pyOpenSSL, PyNaCl, pip, Werkzeug, pyasn1, wheel, jaraco.context) |
| `1093` | MC | This update addresses a security vulnerability (CVE-2025-12454) where certain cookies were not set with the HTTP Only flag, which prevents client-side scripts from accessing cookies and mitigates cookie theft and injection risks |
| `1081` | Security | This update addresses a critical security vulnerability, CVE-2026-34480, affecting the Log4j library used within the Kafka package of the Vertica Database Cluster; the library has been upgraded from 2.17.1 to the recommended fixed version 2.25.4 |
| `1066` | MC | This update addresses the critical security vulnerability CVE-2025-12453, a Reflected Cross-Site Scripting flaw primarily affecting version 10.0.1; prior to this fix, an authenticated attacker could exploit unmanaged input parameters in certain Web UI endpoints to inject and execute arbitrary JavaScript, and the update adds sanitization and neutralization of user-supplied input |
| `987` | Kafka Integration | This update addresses the critical security vulnerability CVE-2025-68161 in org.apache.logging.log4j_log4j-core version 2.17.1 (found during Prisma scans on container_minimal_arm environments); the Log4j core library has been upgraded to 2.25.3 |
| `957` | Admin Tools | Previously, AdminTools restart_node could select a secondary UP node to run the catalog editor for catalog information; it now consistently selects a primary UP node, ensuring correct and up-to-date catalog information |
